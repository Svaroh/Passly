# Беклог завдань та незавершені етапи реалізації Passly

Цей документ містить перелік запланованих до реалізації архітектурних вимог, ендпоїнтів та клієнтських модулів, винесених за результатами аудиту початкового плану (`PLAN.md`).

---

## 1. Серверний API (`passly_api`): Завершення протоколу `sync/1`

Незважаючи на те, що базовий механізм дельта-синхронізації (`/sync/changes`, `/sync/meta` та таблиця `sync_log`) уже успішно впроваджено, наступні компоненти потребують реалізації:

### 1.1. Посторінкова початкова синхронізація (`GET /sync/bootstrap.json`)
- **Мета:** Швидка видача порційного знімка всіх актуальних ресурсів та прав для нових клієнтів або клієнтів із застарілим курсором (`410 Gone`).
- **Компонент:** `plugins/PassboltCe/Sync/src/Controller/SyncBootstrapController.php`, `SyncBootstrapService.php`.
- **Вимоги:**
  - Підтримка курсорної пагінації (`limit`, `cursor`).
  - Видача активних записів без звернення до таблиць історії.
  - Повернення актуального водяного знака `seq` разом із даними для миттєвого переходу клієнта на `/sync/changes`.

### 1.2. Легковагова звірка стану (`GET /sync/manifest.json`)
- **Мета:** Можливість швидкої перевірки цілісності локальної репліки без повторного викачування всіх даних.
- **Компонент:** `plugins/PassboltCe/Sync/src/Controller/SyncManifestController.php`, `SyncManifestService.php`.
- **Вимоги:**
  - Формування хешів або лічильників версій за типами ресурсів і папками.
  - Виявлення локальних розбіжностей або втрачених вікон дельти.

### 1.3. Спеціальна класифікація журналу аудиту `sync`
- **Мета:** Запобігання розростанню журналу `audit_logs` під час масової синхронізації.
- **Вимоги:** Класифікувати читання секретів у рамках дельта-запитів як системні події синхронізації (`sync`), а не ручні перегляди користувача.

---

## 2. Клієнт Android (`passly_android`): Інкрементальна дельта-синхронізація (Етап M3, Вимога R3)

Наразі Android-клієнт використовує механізм повного оновлення `core/fulldatarefresh`. Необхідно задіяти модуль `core/sync` для переходу на повноцінну дельту.

### 2.1. Стратегії обробки дельти
- **Компонент:** `passly_android/core/sync`
- **Завдання:**
  - `DeltaSyncStrategy`: Запит `/sync/changes.json?since={localSeq}` та парсинг доданих, змінених і видалених записів.
  - `ChangesApplier`: Атомарне застосування дельти до бази Room (`secrets`, `resources`, `permissions`) в межах єдиної транзакції.
  - `BootstrapStrategy`: Обробка коду `410 Gone` при застарілому курсорі через виклик `/sync/bootstrap.json`.
  - `ManifestReconciler`: Періодична звірка стану через `/sync/manifest.json`.

### 2.2. Планувальник WorkManager
- **Компонент:** `passly_android/services/sync`
- **Завдання:** Фоновий `CoroutineWorker` з інтеграцією `NetworkStateProvider` та експоненційного бекофу `SyncBackoff`.

---

## 3. Інтерфейс користувача: Керування синхронізацією (Етап M4, Вимога R4)

Клієнтам (Android та браузерне розширення) необхідні явні елементи керування та індикації стану:

### 3.1. Ручний запуск та індикатори
- Кнопка «Синхронізувати зараз» (Sync Now) з візуальним відображенням станів (очікування, синхронізація, успіх, помилка).
- Час останньої успішної синхронізації (наприклад, «Синхронізовано 5 хв тому»).
- Лічильник локальних операцій, що очікують відправки.

### 3.2. Екран налаштувань синхронізації
- Вибір частоти фонової синхронізації (за інтервалом, лише при відкритті, або лише вручну).
- Журнал діагностики та примусова повна звірка.

---

## 4. Офлайн-запис та вирішення конфліктів (Етап M5 та E-E, Вимога R7)

Забезпечення повної автономії при створенні, редагуванні та видаленні секретів без доступу до мережі.

### 4.1. Локальна черга операцій (`pending_ops`)
- Збереження локальних операцій у таблиці `pending_ops` з клієнтськими мітками часу.
- Оптимістичне оновлення локального інтерфейсу з прапорцем `is_pending`.

### 4.2. Вирішення конфліктів (`sync_conflicts`)
- Виявлення конфліктів версій при відправці накопиченої черги (`409 Conflict`).
- Збереження конфліктних копій у спеціальній таблиці `sync_conflicts`.
- Інтерфейс для перегляду та ручного розв'язання конфліктів користувачем.

---

## 5. Аварійний експорт даних (Етап M6, Вимога R8)

Можливість експорту секретів безпосередньо з локального сховища клієнта у разі повної або постійної недоступності сервера.

### 5.1. Автономний експорт
- Експорт локальної бази даних Room/IndexedDB у захищений контейнер KeePass 4 (`.kdbx`).
- Опціональний експорт у JSON (зашифрований або відкритий PGP-бекап).
- Повна незалежність від мережі: розшифрування виконується локально за майстер-паролем та приватним PGP-ключем користувача.
