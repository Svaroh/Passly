# Архітектура автономного клієнта Android (`passly_android`)

Цей документ описує внутрішню архітектуру мобільного клієнта Passly для Android, структуру бази даних, механізми local-first читання, неблокуючу автентифікацію та модуль синхронізації.

---

## 1. Структура локального сховища (Room + SQLCipher)

Клієнт використовує окрему зашифровану базу даних SQLite для кожного акаунта:
`sha256(userId)_resources.db`.

### 1.1 Таблиця `Secret` (Міграція 28 ➔ 29)
Для виконання вимоги **R0 (повна автономність)** секрети зберігаються безпосередньо на пристрої.

```kotlin
@Entity(
    tableName = "secrets",
    foreignKeys = [
        ForeignKey(
            entity = ResourceEntity::class,
            parentColumns = ["id"],
            childColumns = ["resource_id"],
            onDelete = ForeignKey.CASCADE
        )
    ],
    indices = [
        Index(value = ["resource_id"], unique = true)
    ]
)
data class SecretEntity(
    @PrimaryKey
    @ColumnInfo(name = "resource_id")
    val resourceId: String,
    @ColumnInfo(name = "secret_id")
    val secretId: String,
    @ColumnInfo(name = "armored_data")
    val armoredData: String,
    @ColumnInfo(name = "modified")
    val modified: String,
    @ColumnInfo(name = "fetched_at")
    val fetchedAt: Long
)
```

- Секрети прив'язані до ресурсу із каскадним видаленням (`CASCADE`).
- Поле `armored_data` містить оригінальний PGP-armored блок, зашифрований публічним ключем користувача.
- `SecretsDao` забезпечує потокові операції: `upsert`, `deleteByResourceId`, `getByResourceId`, а також реактивні `Flow`.

## 2. Шлях читання даних: Local-First

До впровадження архітектури автономності кожна спроба перегляду пароля, копіювання в буфер чи відтворення TOTP зверталася до віддаленого сервера (`GET /secrets/resource/{id}.json`).

### Новий потік у `SecretInteractor`:
```
UI Запит на отримання секрету (показ, копіювання, TOTP, autofill)
    │
    ▼
[GetLocalSecretUseCase] ─── Знайдено локально? ───► ТАК ──► Розшифрування PGP у пам'яті ──► Повернення результату
    │
    НІ (новий запис, ще не синхронізований)
    │
    ▼
[Перевірка мережі]
    ├─ Немає мережі ──► Помилка: "Секрет відсутній у локальному сховищі"
    └─ Є мережа     ──► FetchSecretUseCase (API) ──► UpsertLocalSecretsUseCase ──► Розшифрування
```

Завдяки цьому всі збережені записи відкриваються **миттєво, без жодного мережевого запиту**.

## 3. Неблокуючий автономний вхід (R6)

Раніше процедура входу (`AuthViewModel.performFullSignIn`) блокувала доступ до інтерфейсу, якщо сервер був недоступний: відбувалося очікування мережевих таймаутів (до 30–60 секунд), після чого з'являлося повідомлення про помилку.

### Архітектура `BackgroundSignInExecutor`:
1. **Перевірка локальної репліки (`HasLocalReplicaUseCase`):** якщо для поточного користувача існує локальна БД та розшифрований приватний PGP-ключ, сховище розблоковується **негайно**.
2. **Локальна валідація:** парольна фраза перевіряється локально за допомогою бібліотеки `gopenpgp` (спроба розблокувати приватний ключ).
3. **Асинхронне встановлення сесії:**
   - Після успішної локальної перевірки користувач **одразу переходить на головний екран (Home)**.
   - Серверна сесія GPGAuth та отримання JWT-токенів виконуються у фоновому режимі (`BackgroundSignInExecutor`) у відокремленому корутинному скоупі.
   - Якщо сервер не відповідає — це ніяк не заважає роботі; застосунок просто фіксує статус «Синхронізація на паузі».

### Мережеві оптимізації:
- Зменшено таймаут підключення (`connectTimeout`) до **10 секунд**.
- Встановлено загальний стельовий таймаут запиту (`callTimeout`) у **60 секунд**.
- Публічні сертифікати PGP та RSA сервера тепер завантажуються **паралельно**, що скоротило час першого підключення вдвічі.
- Транспортні збої (`IOException`, `UnknownHostException`, `SocketTimeoutException`) правильно класифікуються як стан «Офлайн», а не як помилка авторизації.

## 4. Аудит критичного шляху та локальна безпека

Всі сценарії застосунку перевірено на предмет прихованих мережевих залежностей:

- **`AuthenticatedOperationRunner`:** параметр `requiresSession = false` дозволяє локальним операціям (показ деталей, пароля, TOTP) виконуватися без активної серверної сесії.
- **`KeyInspectorViewModel`:** екран деталей ключа зчитує інформацію з локальної таблиці `users`, не надсилаючи запит на `/users/me.json`.
- **`HomeScreen`:** право створення ресурсів (`canCreateResource`) більше не скидається в `false` у разі збою фонового оновлення.
- **`DataRefreshTrackingFlow`:** фонова синхронізація виконується тихо, без блокуючих діалогових вікон, спінерів на весь екран чи сповіщень про помилку зв'язку.

## 5. Модуль `core/sync`

Для підтримки нового дельта-протоколу створено окремий модуль `core/sync`:

- **`SyncStatus`:** стани синхронізації (`Idle`, `Running`, `Offline`, `AwaitingRetry`, `Failed`).
- **`SyncResult`:** результат виконання (`Success`, `Skipped`, `RetryNeeded`, `Error`).
- **`SyncTrigger`:** джерело запуску (`MANUAL`, `BACKGROUND_PERIODIC`, `APP_START`, `NETWORK_RESTORED`).
- **`SyncBackoff`:** сходинчастий інтервал повторів:
  `30s` ➔ `1m` ➔ `5m` ➔ `15m` ➔ `1h` ➔ `6h` (з додаванням jitter).
- **`SyncStatusRepository`:** реактивний стан синхронізації через `StateFlow<SyncStatus>`.
- **`NetworkStateProvider`:** системний моніторинг доступності інтернету через Android `ConnectivityManager`.

---

## 6. Інтеграція з Android Passkey Provider

Клієнт підтримує системну функцію Android Credential Manager:
- `PasskeyCredentialProviderActivity` оптимізовано для роботи без постійного мережевого зв'язку.
- Вибірка облікових даних passkey здійснюється з локальної бази даних.
- Виключено примусовий `RefreshSessionUseCase` з гарячого шляху вибору passkey.
