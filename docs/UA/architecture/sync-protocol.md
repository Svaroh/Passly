# Протокол синхронізації Passly `sync/1`

**Статус:** Нормативна специфікація.  
Серверна частина реалізована в плагіні `PassboltCe/Sync` (`passly_api`), клієнтський каркас — у модулі `core/sync` (`passly_android`).

Протокол є повністю **платформо-незалежним**. Клієнти на Android, у браузерному розширенні, на iOS та Desktop реалізують однаковий формат обміну даними та однакові правила застосування транзакцій.

---

## 1. Фундаментальні інваріанти протоколу

1. **Курсор клієнта — це монотонне ціле число (`seq`), а не часова мітка.** Жодні проблеми розбіжності системних годинників, однакових timestamp-ів під час швидких змін або часових поясів не можуть призвести до пропуску чи втрати події.
2. **Локальна база — самодостатнє сховище.** Синхронізація є факультативним сервісом доставки оновлень. Відсутність синхронізації впливає лише на свіжість даних, але ніколи на їхню доступність.
3. **`deletions` містить відкликання прав доступу.** Якщо в користувача забрали право на ресурс або виключили його з групи, для клієнта це повертається як звичайне видалення (`deletion`). Це робить дельту самодостатньою.
4. **Жодна помилка протоколу не є фатальною для локальних даних.** Відповідь `410 Gone` означає «виконайте bootstrap поверх наявних даних», а не «очистіть сховище».
5. **Атомарність застосування сторінки:** кожна порція змін (`batch`) застосовується в локальній БД в єдиній ACID-транзакції разом із записом нового значення курсора. При обриві мережі наступний запит продовжується точно з останнього підтвердженого курсора.

---

## 2. Словник термінів

| Термін | Значення |
|--------|----------|
| **`seq`** | 64-бітне беззнакове монотонно зростаюче число (`BIGINT UNSIGNED AUTO_INCREMENT`), що присвоюється кожній зміні в системі сервером. |
| **`cursor`** | Найбільший номер `seq`, який клієнт успішно отримав, застосував та зафіксував у своїй локальній БД. |
| **`epoch`** | Унікальний ідентифікатор інстансу бази даних сервера. Якщо сервер було відновлено з бекапу або перевстановлено (зміна `epoch`), клієнт ініціює новий bootstrap. |
| **`watermark`** (водяний знак) | `MAX(seq)` серед записів журналу, старших за `WATERMARK_LAG` (за замовчуванням 2 секунди). Необхідний для запобігання пропуску подій при тривалих транзакціях бази даних. |
| **`upsert`** | Створення або оновлення сутності, що передається у вигляді повного DTO. |
| **`deletion`** | Ідентифікатор сутності, яка була фізично видалена на сервері або стала недоступною користувачеві через зміну прав. |

## 3. Серверний журнал змін (`sync_log`)

Журнал реалізовано в окремій таблиці MySQL/PostgreSQL у міграції `V600CreateSyncLog`:

```sql
CREATE TABLE sync_log (
  seq         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  entity_type VARCHAR(32) NOT NULL,
  entity_id   CHAR(36) NOT NULL,
  op          VARCHAR(16) NOT NULL,
  created     DATETIME(6) NOT NULL,
  INDEX (entity_type, entity_id),
  INDEX (created)
);
```

### Принципи ведення журналу:
- **Один рядок на подію, без збереження корисного навантаження (payload).** Корисне навантаження формується динамічно під час виклику API, щоб права доступу завжди перевірялися проти **поточного** стану дозволів.
- **Трансляція подій дозволів:** події змін прав (`permissions`) та членства в групах (`groups_users`) транслюються в події на відповідних ресурсах або папках, оскільки саме їхня видимість змінюється для користувачів.
- **Ретеншн (зберігання):** записи, старші за 90 днів, автоматично видаляються консольною командою `bin/cake sync_log_prune`. Якщо клієнт звертається з курсором, що вже був видалений, сервер повертає `410 Gone`.

## 4. Специфікація API-ендпоїнтів

### 4.1 `GET /sync/meta.json`
Повертає метаінформацію про серверну підтримку протоколу. Викликається під час налаштування акаунта або періодичної перевірки сумісності.

```json
{
  "header": { "status": "success" },
  "body": {
    "protocol": "sync/1",
    "epoch": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
    "min_client": "6.0.0",
    "max_page_size": 500,
    "retention_days": 90
  }
}
```

### 4.2 `GET /sync/changes.json?since=<seq>&limit=500`
Основний робочий ендпоїнт інкрементальної дельти.

#### Параметри запиту:
- `since` (обов'язковий): поточний курсор клієнта (ціле невід'ємне число).
- `limit` (опційний, за замовчуванням 500): максимальна кількість подій журналу для обробки.

#### Приклад відповіді:
```json
{
  "header": { "status": "success" },
  "body": {
    "cursor": 148213,
    "has_more": true,
    "upserts": {
      "resources": [
        {
          "id": "e2c3b4a1-0000-4000-8000-000000000001",
          "name": "Production Database Credentials",
          "username": "dbadmin",
          "uri": "https://db.internal",
          "description": "Primary Postgres cluster",
          "modified": "2026-10-16T12:00:00Z",
          "permission": { "type": 15 },
          "favorite": false
        }
      ],
      "secrets": [
        {
          "id": "s1c3b4a1-0000-4000-8000-000000000001",
          "resource_id": "e2c3b4a1-0000-4000-8000-000000000001",
          "data": "-----BEGIN PGP MESSAGE-----\nwcBMA...",
          "modified": "2026-10-16T12:00:00Z"
        }
      ],
      "folders": [],
      "users": [],
      "groups": [],
      "resource_types": [],
      "metadata_keys": []
    },
    "deletions": {
      "resources": [
        "d4c3b4a1-0000-4000-8000-000000000099"
      ],
      "folders": [],
      "users": [],
      "groups": []
    }
  }
}
```

### 4.3 `GET /sync/bootstrap.json?limit=500&page=N`
Повне початкове завантаження для нового пристрою або у разі отримання `410 Gone`.

- За один прохід повертає ресурси **разом із зашифрованими блобами секретів**, забезпечуючи досягнення повної автономності (R0) вже на етапі завершення першого входу.
- Значення `cursor` фіксується на першій сторінці запиту та повертається незмінним на наступних сторінках.
- Клієнт зберігає дані сторінка за сторінкою, тому при перериванні зв'язку завантаження відновлюється з поточної сторінки.

### 4.4 `GET /sync/manifest.json?type=resources`
Легковажна періодична звірка стану (механізм самолікування):
```json
{
  "header": { "status": "success" },
  "body": [
    {
      "id": "e2c3b4a1-0000-4000-8000-000000000001",
      "modified": "2026-10-16T12:00:00Z",
      "secret_modified": "2026-10-16T12:00:00Z"
    }
  ]
}
```
Клієнт порівнює маніфест зі своєю локальною таблицею. У разі виявлення розбіжностей відсутні елементи довантажуються цільовими пачками (`filter[has-id][]`).

## 5. Алгоритм роботи клієнтського циклу

```
┌─────────────────────────────────────────────────────────────┐
│                    Клієнтський виклик                       │
│                   sync(trigger: Trigger)                    │
└──────────────────────────────┬──────────────────────────────┘
                               │
                [Мережа доступна?] ─── НІ ──► Повернути SyncResult.Skipped(NoNetwork)
                               │
                              ТАК
                               │
               [Відправка черги pending_ops]
                               │
               [Курсор збережений?] ─── НІ ──► Виконати bootstrap()
                               │
                              ТАК
                               │
        ┌──────────────► Запит GET /sync/changes.json?since=cursor
        │                      │
        │             [Статус 410 Gone?] ─── ТАК ──► Виконати bootstrap() поверх локальних даних
        │                      │
        │                     НІ
        │                      │
        │               [ACID Транзакція]:
        │               - застосувати upserts
        │               - застосувати deletions
        │               - зберегти новий cursor = page.cursor
        │                      │
        └─────── ТАК ── [has_more == true?]
                               │
                              НІ
                               │
        [trigger == MANUAL або настав час звірки?] ── ТАК ──► reconcileAll() (manifest)
                               │
                              НІ
                               │
                  Повернути SyncResult.Success
```

## 6. Матриця реакції на помилки

| Ситуація | Дія клієнта | Стан локальних даних |
|----------|-------------|----------------------|
| **Відсутній інтернет / DNS-збій / сервер вимкнено** | Статус «Не синхронізовано», експоненційний backoff. | Повністю доступні для читання, пошуку, розшифрування та локальних операцій. |
| **401 Unauthorized / Сесія прострочена** | Фонова спроба повторної автентифікації; якщо невдало — зупинка синхронізації. | Локальні дані залишаються недоторканими, сховище відкрито. |
| **410 Gone (курсор за межами 90 днів)** | Виконання інкрементального bootstrap поверх локальних даних. | Локальні дані не видаляються, а оновлюються та доповнюються. |
| **Зміна epoch сервера** | Автоматичний повторний bootstrap. | Локальні дані оновлюються, відсутні записи актуалізуються. |
| **5xx Server Error / Мережевий таймаут** | Backoff: 30 с → 1 хв → 5 хв → 15 хв → 1 год → 6 год. | Застосунок продовжує працювати без сповільнень. |
| **Помилка розшифрування метаданих v5** | Сутність позначається прапорцем `undecryptable`. | Решта записів сторінки успішно зберігаються в базі. |
